# Govern Change Records, Pull Requests, and Releases

## Status

Accepted

## Date

2026-08-12

## Scope

Changelog records, ADR responsibility, release traceability, branches, commits, peer review, and merging to `main`.

## Context

The repository merges pull requests directly into `main`, making each merged pull request materially released. Change summaries must remain easy to scan while very important decisions retain their reasoning and consequences.

The repository also needs a traceable relationship between branches, commits, pull requests, changelog versions, and review. Without one explicit governance contract, a pull request can gain multiple versions, use ambiguous identifiers, mix unrelated work, or merge without independent review.

## Decision

### Changelog and ADR Responsibilities

`CHANGELOG.md` records concise summaries of what changed. An ADR records why a very important, durable decision with broad or difficult-to-reverse consequences was made.

Create ADRs only when the threshold in `docs/adr/README.md` is met. Routine implementation choices, minor documentation or presentation decisions, fixes, content corrections, and ordinary maintenance do not require ADRs.

Keep the active changelog at the repository root. Use `docs/old-version/` only during intentional archive maintenance.

### One Pull Request, One Version

The repository does not use an `Unreleased` section.

Every new pull request creates exactly one semantic version and dated changelog section. All notable human and AI-assisted changes in that pull request are recorded under the same version. Additional changes within the same pull request update that section and do not create another version.

When the pull request boundary cannot be determined reliably, include the GitHub PR number in the version heading. If no PR number is available, use the first verified commit SHA that actually belongs to the pull request. Base commits, unrelated commits, branch names, invented identifiers, and placeholders are prohibited.

### Branches and Commits

Every pull request uses one dedicated branch and targets `main`. Direct contribution commits to `main` are prohibited.

Branch names use `<label>/<intent-summary>`:

- `feat` adds new work.
- `fix` changes, repairs, corrects, or alters existing work.
- The intent summary uses lowercase kebab-case with no more than five hyphen-separated words.

Commit messages use `<label>(<optional-scope>): <imperative summary>`:

- `feat` adds a new non-Markdown capability.
- `fix` covers other non-Markdown changes, repairs, alterations, refactors, maintenance, and security corrections.
- `docs` applies whenever a commit changes Markdown.

One branch maps to one pull request and one changelog version. Review corrections remain on that branch and update the existing pull-request version.

### Peer Review and Merge

Before merge, at least one reviewer other than the pull request author must approve the pull request. The author cannot satisfy the required peer approval.

All requested changes and review conversations must be resolved. Applicable verification must be complete before merging to `main`.

## Consequences

- Changelog summaries and important decision reasoning have separate, explicit owners.
- Every changelog entry belongs to one semantic version and date.
- One pull request corresponds to one branch and one release version.
- All human and AI-assisted changes remain within the pull request's version record.
- Ambiguous history uses a verified PR identifier rather than a placeholder or unrelated commit.
- Branch and commit purpose is detectable from the defined label sets.
- Every merge to `main` receives at least one independent peer review.
- Routine decisions do not create unnecessary ADRs.
